02

Semgrep is the most valuable row

Semgrep is not a weak competitor, and pretending otherwise would sink the writeup. It is a mature, well-engineered static analyser, and on this corpus it scores 5.7% FPR-on-traps at 87.5% precision. Any claim that existing tooling is simply bad does not survive contact with it.

What makes it the most useful row in the table is where its recall goes:

Code surface 78%
Reasoning surface 48%

Undeclared network egress: 6 of 6, as good as this project. Undeclared exec: 3 of 3. Annotation lies: 0 of 1. Return-value injection: 0 of 2. Progressive-disclosure payloads: 0 of 1.

§02 predicted this in one sentence — "Read only the code and you miss a poisoned description entirely; the code is clean." A tool that reads the implementation finds what the implementation does. This is that claim, confirmed by somebody else's tool rather than by mine.

!

And its attribution is 0%. Not one of semgrep's 14 true positives named the actual attack. It reports subprocess with shell=True; it never reports this server never said it would spawn processes, because it has no representation of what the server claimed.

Its detections on the malicious stratum are largely incidental — right answer, wrong reason. That is not a criticism of semgrep, which is doing exactly the job it was built for. It is the measurement that says the reasoning surface needs analysis of its own.

mcp-shield, an actual MCP scanner, scores 19.0% FPR-on-traps at 20% precision and completed on only 60% of the corpus. Included at its real numbers rather than quietly omitted.

03

The bug this checkpoint was worth

!

divergence scan had never called the divergence engine. Since P3, the shipped CLI ran only the declared-interface analyzer. The project's headline capability was missing from the actual product for two entire phases while every benchmark number said otherwise.

Tests missed it because they call analyzers directly and the benchmark goes through the adapter — so the one path a real user takes was the one path nothing exercised. Fixed by giving the CLI and the adapter a single shared composition point, plus ten end-to-end tests that invoke the CLI the way a person would.

Two more from the holdout expansion, 10 → 26 artifacts:

  • The holdout harness never ran A2. It had been blind to the declared-interface checks the whole time it was supposedly guarding them.
  • allowed-tools: [Read, Grep] parsed to zero capabilities. Valid YAML, written that way by real skills, and it would have falsely flagged every one of them.

And a fourth, found by CI after the push

The first real workflow run failed at Upload SARIF. Code scanning rejected the file outright:

Error: Code Scanning could not process the submitted SARIF file:
SARIF URI scheme "code-review-pro" did not match the checkout URI scheme "file"

Two bugs, both mine:

  • Prose evidence became a URI. Fleet findings carry evidence like code-review-pro: publisher=unknown, signed=None — good evidence, not a location. It went into artifactLocation.uri, and GitHub parsed the leading code-review-pro: as a URI scheme.
  • Valid paths were relative to the wrong root. The base parameter was accepted and never used, so scripts/collect.py was emitted artifact-relative — a path that does not exist in the checkout, pointing every alert at nothing.

My ship-checkpoint verification is what let this through. I validated SARIF against a single-artifact scan, where evidence really is server.py:18 — the one case that worked. I never generated SARIF from a fleet run, which is precisely what the workflow uploads. Checking the happy path and calling it verified is the same mistake as the CLI bug above, one level up.

Fixed by making _split_location return a path only when the evidence is path-shaped, keeping prose in properties.divergence.evidence so no finding loses its evidence, rebasing locations onto the repository via the roots the caller already knows, and anchoring location-less findings to the scanned file. A --check validator now runs in CI before upload — rejection is all-or-nothing, so one bad URI silently discards every finding in the file.

All three are the same shape: the corpus is 80 artifacts in one house style, written by one person, and anything outside that style was untested. That is the argument for the holdout set, and it keeps paying.

The scanner that could not be benchmarked

mcp-scan — the most-cited open-source scanner in this space — is now snyk-agent-scan, a Snyk product at v0.6.0. It is absent from the table for a reason worth reporting as a result rather than a gap:

  • It transmits tool descriptions to a hosted Snyk analysis API. There is no offline mode — --analysis-url only redirects the verification server.
  • It requires a SNYK_TOKEN from a Snyk account, and exits 1 before scanning anything without one.

A benchmark that cannot be reproduced without a vendor account is not reproducible. §09 requires runs to be fully reproducible offline after the first pass; a hosted analyser behind account registration fails that twice over. Its adapter now reports itself unavailable with that reason rather than silently scoring zero — an absent competitor must never read as a beaten one.

The observation cuts further than one missing row. For the artefact under examination — an agent's installed configuration, which §10 notes "is itself sensitive" — a scanner that ships that configuration's metadata to a vendor is making a trade the user should get to see. It also explains why semgrep is the more useful competitor: offline, no account, and therefore actually re-runnable by a reader.

The honest caveat, unchanged. The corpus was written by the same person who wrote the scanner, and the scanner was tuned until the corpus came back clean. Two independent competitors in the table help. A 26-artifact holdout that keeps finding real bugs helps more. Neither makes the result self-validating, and the writeup says so in its own section rather than in a footnote.
