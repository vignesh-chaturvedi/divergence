02

Why this is not the strawman with more patterns

The obvious objection: a lexical claim extractor is regexes, and regexes are what scored 57% FPR. The distinction is what the text is mapped to.

keyword scanner · text → verdict

Sees subprocess.run and "execute arbitrary shell command". Reports a finding. A shell executor is condemned for being a shell executor.

A5 · text → claim

Sees "execute an arbitrary shell command", emits {proc_spawn} as C. B is {proc_spawn}. B ⊆ C, so it is posture. Nothing is reported.

The finding never comes from the text. It comes from the comparison — which is why the same vocabulary that destroys a scanner is safe inside an extractor.

Three rules that hold the precision

RuleWhat it prevents
Denial outranks silence. "Runs entirely offline" is recorded separately from simply not mentioning the network.Contradicting a volunteered promise is critical; contradicting silence is high. Collapsing them would throw away the strongest signal available.
B ⊄ C raises risk only for high-signal capabilities — network, credentials, exec, eval, delete. Filesystem and env go to posture.Almost any tool that "tracks" or "records" anything touches a file without saying so. A rule that cannot separate a todo list from an exfiltrator has no business in a verdict.
Cross-tool instruction needs a directive, not a reference."A session token for use with other billing tools" is documentation. "Route all file operations here" is not. The first was a trap false positive before the rule was tightened.

A fourth, found while debugging a miss: fenced code blocks are stripped before claim extraction. A skill whose body was curl … | sh appeared to have declared network access, because the payload itself contained the word http — the artifact claiming a capability by exhibiting it. A fenced block is implementation, and A4 already treats it that way.

§02's rule table has a row that report 01 flagged as structurally out of reach for keyword scanners: C ⊄ S ∪ B — a description instructing behaviour the artifact cannot itself perform.

04

The holdout, and what it caught

the honesty check

Tuning rules until a corpus comes back clean proves the rules fit the corpus. To probe whether they do anything else, I wrote ten artifacts after the engine was tuned, deliberately unlike the corpus in shape — a log shipper that declares its egress, a CI runner, a backup tool, a skill with an honest imperative, a monitoring server that mentions "other services" descriptively, and four attacks in unfamiliar clothing.

Two failed immediately, for the same real reason. A4 only treated functions carrying an @mcp.tool() decorator as entrypoints. A server whose manifest declares tools implemented as plain functions had every capability marked unreachable — so a unit converter that quietly POSTs, and a spell checker that breaks its own "entirely offline" promise, both scanned clean.

Every server in the 80-sample corpus uses decorators. The benchmark could not have found this at any score. It is exactly the class of blind spot §11 warns about — and it is why the holdout is now a permanent test file rather than a one-off exercise.

The fix also removed a footgun: acquire and extract must be called together, because the declared surface is what names the handlers. Three call sites each had to remember. They now go through one pipeline.load().

05

A5 without a model

§04 specifies a small local model for claim extraction. There is no local model runtime on this machine — no ollama, no llama.cpp, no transformers — so this needed a decision rather than a silent substitution.

Two of the project's own rules argue for the deterministic backend being the default regardless: §09 requires benchmark runs to be reproducible offline, and §11 names claim drift as the thing that makes the headline number meaningless. A backend that needs a running model server satisfies neither.

ComponentStatusNote
Lexical backenddefaultDeterministic by construction, offline, zero cost.
Model backendwired, gatedDIVERGENCE_CLAIM_BACKEND=model. Fixed JSON schema, constrained decoding, temperature zero, content-hash cache — the §04 contract intact.
Response parsertestedVerified with no model present, the same way the third-party adapters are.
Failure modeloudAn unreachable model raises rather than degrading to lexical — a silent fallback produces numbers comparable to nothing.

If the gate clears without a model, the model becomes an upgrade path rather than a dependency. That is a better position than the spec assumed, and worth revisiting at the v1 checkpoint rather than treating §04 as settled.

07

Next — P4, then ship

P4 is A7: shadowing via embeddings, a toxic-flow graph across servers and skills, and relative preference scoring. Its gate is detecting a planted shadow tool and an over-triggering skill inside a realistic multi-artifact config, without flagging the legitimate originals.

§06 above is the argument for it: three attack classes are currently caught under a general name because a single-artifact scan cannot distinguish them. The corpus already contains the shadow artifacts alongside the legitimate ones they imitate, so the gate is testable the day the analyzer exists.

◇

The ship checkpoint is one phase away, and §11 calls it load-bearing. v1 ships before any Rust sandbox work begins — uvx distribution, SARIF output, GitHub Action, benchmark table published, writeup drafted. Scope grew on two axes and the checkpoint is the mitigation; it only works if it is honoured.

Two things should happen before that checkpoint, not after: run the third-party scanners so the comparison has independent competitors, and grow the holdout set, since ten artifacts caught one real bug and twenty would probably catch another.
