The core rule, working

The clearest demonstration is a matched pair from the corpus. Two artifacts read the same credential path with the same API call. One is a finding; one is not.

trap-priv-009 · SSH server

Reads ~/.ssh/id_rsa because it opens SSH connections, and says so. 0 risk findings. One posture note: reaches credential-bearing paths.

skill-mal-003 · linter

Declares allowed-tools: Read, then opens a socket and spawns a subprocess. 1 risk finding, with the grant it broke and the line that broke it.

$ divergence scan corpus/samples/agent_skill/malicious/skill-mal-003-.../artifact

  capabilities net_outbound, proc_spawn

  RISK — divergence between what it says and what it does
    [high] script_exceeds_allowed_tools
      bundle reaches net_outbound, proc_spawn but allowed-tools grants only fs_read
      claim:    SKILL.md: allowed-tools = Read
      evidence: scripts/lint.py:7

  POSTURE — capability, not a verdict
    [low] combines subprocess execution with outbound network access
      scripts/lint.py:5

Both halves of the contradiction are attached to every risk finding — the exact claim and a file:line — and a test asserts it across all detections. §04 requires this, and it is what makes output reviewable rather than merely alarming. Posture fires 65 times across the corpus and moves no verdict; the strawman has no posture channel at all, which is most of why it fails.

03

Two false positives caught in review

both fixed

Running /code-review before closing the phase found two bugs that the benchmark could not have caught, because neither shape exists in the corpus. Both were latent false positives — the expensive kind of error here.

BugWhat it didWhy the corpus missed it
A bare URL counted as network capabilityA read-only skill citing its own documentation was flagged for exceeding allowed-toolsNo corpus skill has both a restrictive grant and a documentation link. In the wild that combination is everywhere.
Capability attributed artifact-wide, not per toolA server exposing an honest reader beside an honest writer had the reader blamed for the writer's write_textEvery annotated corpus server has exactly one tool. Most real servers have both readers and writers — this would have been the most common false positive in the field.

The first fix says a documentation link is a reference, not an action — only curl, wget or a fetch( counts. The second is a scope admission: attributing a sink to one specific handler needs reachability from each entrypoint, which is P2's job, so P1 now asserts an annotation lie only when no sibling tool can account for the mutation. Neither fix cost any detection — the benchmark was unchanged at 100% precision. Both carry regression tests.

The lesson is about the corpus, not the code. An 80-sample benchmark cannot cover shapes nobody thought to author. Both bugs were found by reading, not by measuring. Worth carrying into P2, where the analysis gets much harder and the temptation to trust the number gets much stronger.

Two capability-model rules that prevent whole false-positive classes

  • Bash grants everything. Understating it would flag any honest skill that declares Bash and then spawns a subprocess.
  • An absent allowed-tools is unrestricted, not empty. Treating absence as the empty set would make every undeclared skill appear to exceed its permissions — a false-positive stratum on its own.
  • Reading a credential file is a filesystem read. SECRETS_READ coarsens to FS_READ when checking a grant, or every honest credential manager becomes a finding.

These are recorded in docs/adr/0002 and flagged in CLAUDE.md as things not to "simplify" later. Each one looks like an over-permissive shortcut until you see the false positives it prevents.

06

Next — P2, static behaviour extraction

P2 is tree-sitter grammars for TypeScript, Python and shell; capability sets from actual API surface; reachability from handler and script entrypoints; then parameter taint into sinks. Its gate is capability sets manually verified on 50 real artifacts, with our own false-negative rate published.

The P1 probe is the thing P2 replaces, and review already named its two weaknesses precisely: no per-handler attribution (which forced the sibling-tool guard) and no reachability (a sink in dead code counts). Both are exactly what reachability from entrypoints fixes, so P2 should let the annotation check become per-tool and recover the recall the guard currently costs.

§07 says to expect P2 to overrun, and that shell will fight you. The corpus already contains shell payloads in skill bundles and markdown prose, so that fight is measurable from day one rather than discovered at the gate.
